# Coach context and tools

## Prompt Projection & Context Budgeting
To optimize API token consumption and response latency, Pacecraft uses a strictly bounded context projection rather than dumping entire databases into prompts:
- **Request Profiles**: General coaching, today's training, activity analysis, weekly planning, plan edits, competition preparation, profile/check-in, provider sync and attachments select different projections. Selection is not an authorization decision.
- **Activity Projection**: Routine turns include the newest completed activity per sport; planning and analysis retain up to five. Exact activity details remain available through the existing read tools. A strength session counts with its total time: its compact row names `elapsed_duration_s` instead of `moving_duration_s`, the session tools state that rule, and the weekly strength volume and activity rollup hours sum the total time; other sports keep their moving time.
- **Planning Projection**: Routine turns include a three-day outlook and two recent days; weekly planning includes a 14-day outlook. The day-by-day planning view (recovery, illness/check-ins, weather, calendar markers) rides only on planning, morning check-in and today-training turns and carries calendar events once, in the external calendar section. Review kinds (progress, block) have no future horizon, a session analysis at most two days ahead, and a progress review no training-plan list. A typed planning request ("Plane meine nächste Woche", "Plane die nächsten 4 Wochen", "Passe die Woche an") gets the same planning brief and playbook as the matching quick action. A typed review of one session ("Wie lief mein Intervalltraining?"), of progress ("Zeig mir meinen Fortschritt", "Werde ich fitter?") or of a block ("Bewerte meinen letzten Block") gets that review's playbook and keeps the sections the message itself asked for; questions about a period, recovery after a session, or advice keep their own selection. Confirmed profile constraints, competitions and labeled current performance remain available; every omitted section stays loadable with `read_coach_context`. The request-size diagnostics log the selection name, request kind and per-section characters.
- **On-Demand Details**: `read_coach_context` loads selected omitted local sections without a provider refresh. Its output is bounded to 40,000 characters and marks incomplete results. Successful reads also expose remaining tools already permitted for the turn, without granting mutation or remote-write authorization.
- **Conservative Fallback**: Pending requests, short continuations, explicit provider refresh/sync requests and long-range or explicitly dated planning retain full bounded context and tools. A clear topical request does not select full training context merely because it contains a pronoun such as "das" or "diese". The 120,000-character training-context cap, model selection, attachment handling and output-token limits remain unchanged.
- **Refresh Follow-Ups**: After refresh results, the Coach rebuilds current data using the original request topic and attachment context. Existing tool receipts retain dialogue continuity without automatically expanding all training sections or tools.
- **Library Selection**: Template descriptions are included for planning, not ordinary questions; library read tools remain available when details are needed.
- **Metric Sanitization**: Raw JSON payloads from providers are stripped down to core athletic parameters (FTP, TSS, RPE, Heart Rate, Power Zones, Duration, Distance).
- **No Stored Responses**: Coach requests use `store: false` and `include: ["reasoning.encrypted_content"]`; within a turn each tool round resends the earlier items instead of a `previous_response_id`. Only the attachment conversation stays stored; see [operations](operations.md). Every request is streamed inside the durable local job, which sends the text to the open chat when one is attached and drops it otherwise. A turn interrupted by a restart is requested again from its original input and the tool results already saved; saved tool results are replayed, not run twice, and the new answer may be worded differently. A streamed response may stay silent for up to 10 minutes before it counts as timed out and is requested again (up to three attempts for a transient provider failure).
- **Dialogue Pruning**: Routine requests send up to eight recent messages and three completed-action receipts. Pending work, pronoun references and continued tool work retain the full bounded dialogue and source IDs; authorization still uses the original local dialogue. The current user message is sent once, separately with its source ID, and request JSON omits unnecessary separator whitespace. Remote conversation chains are pruned between distinct command sessions.
- **Size Diagnostics**: Context profiles, section character counts and request/tool-schema sizes are recorded without athlete content. The diagnostic capture of a Coach request to OpenAI can hold the sanitized request body, including dialogue and training context, for up to 7 days; the diagnostic report states this. Character counts are not provider token measurements; synthetic reduction tests do not establish live quality or latency.
- **Context Preview**: The preview remains a full local context overview; actual request selection depends on the message subsequently sent.

## Tool Execution & Reversible Changesets
The Coach interacts with the athlete's data via structured tools covering plan inspection, template management, profile editing, nutrition correction, and provider synchronization:
- **Receipt Retention**: While a turn is open, its receipt keeps the full tool results. The final or failure receipt keeps only status, identifiers, proposed actions and the undo references, so stored receipts hold no bulky tool output. Progress updates write only the changed receipt keys. Receipts follow `DATA_RETENTION_DAYS`, except those whose changes can still be undone.
- **Transaction Locks**: All database updates share SQLite transaction locks to guarantee that conversational actions and background syncs never collide.
- **Revision Control**: Plan modifications require passing the current planning revision and object hash, preventing overwrite collisions if edits occur concurrently.
- **Named Remote Sync**: An Intervals.icu or Garmin write the athlete names in their own message runs in the same turn without an approval card, bound to the stored units, payload hashes and manifests as a card would bind it; the receipt lists the queued sync and each remote deletion it carries. An unclear request gets an offer instead. Only an explicit Garmin removal still shows a card, bound to the current session and originating Coach turn; a changed or stale manifest fails closed.
- **Receipt Verification**: Tool invocations produce structured receipts in the chat UI, distinguishing saved local modifications, pending approval, queued sync jobs, and rejected parameters.

## Multimodal Capabilities
- **Voice Transcription**: Push-to-talk voice recording captures audio directly in the PWA. Audio is streamed to `/audio/transcriptions` in memory and inserted into the message box. Raw audio is never persisted.
- **File Attachments**: Athletes can attach up to 4 GPX, FIT, or image files per turn: GPX and FIT up to 5 MB each; the browser accepts images up to 15 MB and downsizes them before upload, and the server accepts at most 5 MB per decoded file. The app parses GPX and FIT files locally and sends OpenAI the parsed measurements (every point with time, elevation, speed, heart rate, power and cadence) plus a computed summary, never the original file. The first and last 500 m of every track have no position (the other values of those points stay), and GPX author, device and name data, FIT device and serial-number records and the FIT user profile are left out. Images are sent for vision-based AI coaching with EXIF, XMP, comments and other metadata removed (JPEG, PNG, WebP; an image that cannot be parsed is rejected); the athlete's stored copy stays unchanged.
