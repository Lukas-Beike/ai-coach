# Synchronization and jobs

## Background Scheduling Engine
- **Startup**: On launch, `server.py` composes configuration, persistence, providers, HTTP routes and workers; startup initializes the database and enqueues configured refreshes.
- **Hourly Provider Cycle**: The scheduler loop wakes every 300 seconds. Calendar, Garmin and Wahoo refreshes become eligible once their latest attempt or success is at least 3,600 seconds old; weather refreshes are queued on a pass when a location is configured, no weather job is active, the 3-hour forecast cache has expired and no retry backoff after a failure is pending. Startup and manual weather refreshes still force a fresh read.
- **Garmin Recent History**: Manual activity synchronization defaults to 84 days for Garmin and Wahoo. Automatic Garmin synchronization first loads 84 days of activities, sleep, HRV, daily statistics and resting heart rate where supported. Subsequent hourly refreshes normally read today and yesterday; the first refresh of each local day re-reads the last 7 days so late watch uploads replace partial values. Slowly changing metrics (heart-rate zones, gear, race predictions, VO2 max, FTP and lactate threshold, endurance score, running tolerance and their histories) are read on that first daily refresh and after a new activity; other refreshes keep their stored values and freshness. Successfully read continuous date windows are retained per collection; failed collections do not advance their coverage. After an outage, refreshes catch up from the oldest collection endpoint with overlap, bounded to 90 days per request. Historical activity backfills do not advance recovery coverage. A one-off Garmin wellness backfill (`wellness_backfill`, cursor `wellness_history`) walks the same 90-day chunks back to `SYNC_HISTORY_EARLIEST_DATE` after startup and resumes after a restart: it reads full sleep nights (SpO2, respiration, sleeping heart rate), HRV, daily summaries with resting heart rate, and weigh-ins, adds only days not stored yet (a stored night without night values gains them), and never deletes. A second one-off backfill (`rating_backfill`, cursor `rating_history`) stores the watch ratings that only the Intervals.icu activity copies still hold: for each session with an Intervals.icu RPE or feel and a Garmin copy without a stored rating it reads the Garmin single-activity summary (30 activities per job, paced, newest first, one Personal API token per job, resumable after a restart) and stores RPE and feel as Garmin ratings. A rate limit retries later; only a rejected key exchange stops it and shows the key hint; an activity that fails three runs or answers with a client error is skipped and counted; sessions without a Garmin copy are only counted. It finishes for good once the Garmin and Intervals.icu activity histories reached `SYNC_HISTORY_EARLIEST_DATE`, and never reads before it. The diagnostic report counts it in `rating_backfill` (counts only). A third one-off backfill (`stream_backfill`, cursor `stream_history`, Garmin and Wahoo) re-fetches the full-resolution record streams that the Intervals.icu purge left missing: it walks the sessions newest first back to `SYNC_HISTORY_EARLIEST_DATE` and downloads the original FIT file of each non-manual, non-strength record that has no full-resolution stream set yet (Garmin: the Personal API file download, 30 files per job, 2 s apart, one token per job, so a Personal API key is required; Wahoo: the download links of the workout list, 100 files per job, 1 s apart). It stores the stream and device-lap sets exactly like the regular detail fetch, never touches strength sets and writes nothing to a provider. A rate limit retries later and keeps the cursor; a rejected key stops it and shows the key hint; a record without a file or without sensor data is counted and not read again; a download that fails three runs or answers with a client error is skipped (the job still completes and the chain reads the rest of the window) until the finished chain is queued again without `end_date` (`POST /api/sync/jobs`). Without a Personal API key Garmin stays blocked and says so until the next app start. The diagnostic report counts it per provider in `stream_backfill` (counts only).
- **Analysis Coverage**: Charts expose the number of available dated values; recovery charts show measured days and the earlier nights of the 42-day comparison. Training focus shows locally known Garmin sessions and their observation dates. Missing measurements and recordings remain unknown, never confirmed zeros or rest days.
- **Periodic Synchronization Loop**: Each loop pass enqueues eligible calendar, Garmin and Wahoo refresh jobs and runs the morning Body Battery refresh. The loop uses the athlete's local clock for provider freshness markers; there is no fixed 03:00 daily run.
- **On-Demand Refreshes**: The UI and Coach can enqueue provider, calendar and weather refresh work through the documented API routes. When the athlete explicitly asks the Coach for current data, the Coach waits for the Garmin and Wahoo refreshes (where configured) to finish before answering instead of queueing a job; a Garmin refresh also updates the morning Body Battery, and the answer notes when it finished only partially. Calendar and weather refreshes stay queued.

## Priority Queue & Durable Job Processing
Conversational turns are persisted in `coach_commands`; provider synchronization and background work use durable jobs in `sync_jobs`.
- **Streaming Handshake**: When an HTTP turn starts, Server-Sent Events (SSE) immediately return the durable job UUID.
- **Decoupled Execution**: If the athlete locks their phone or loses cellular connection, the server continues execution uninterrupted.
- **Recovery on Reconnect**: Upon reconnection or app reload, the PWA polls the durable job result using its UUID, rendering the completed answer without re-executing actions.
- **Visible Provider Failures**: OpenAI API credit, quota, spending-limit, access, rate-limit, unavailable-model, conversation-state, timeout, and service-unavailability failures produce a clear recovery instruction in the chat history, including classified failures reported inside an HTTP-200 response stream. The message remains visible after reload; private provider error text is not shown. Unknown failures use a safe technical-error message with retry and diagnostic-export guidance.
- **Busy Local Database**: When no database connection becomes free in time, a sync or a recorded Coach turn failure shows a short German retry message instead of a technical one, also when the database was busy after a provider answer arrived. Any other HTTP request, including login and starting a turn, answers with a retryable HTTP 503 (`reason: database_busy`, a `Retry-After` header and `retry_after_seconds`) instead of a server error. Login and logout wait at most 10 seconds for the writer and never queue behind startup syncs or the canonical backfill, which yield the writer to waiting requests between their transactions. A Coach turn failure that cannot itself be stored keeps the generic server error. A sync that fails this way is queued again like a network error and never raises the manual-attention notice of the status strip. Older stored English errors stay until the next successful sync.

## Provider Data Handling
- **Garmin Sleep Gate & Body Battery**: Morning synchronization deliberately halts until Garmin's sleep window completes. Body Battery tracking captures the final pre-sleep value and the wake-up value within 60 minutes of rising, retrying up to 3 times with 15-minute intervals. Besides the morning read, the first Garmin refresh of each local day reads the Body Battery reports of the last 7 days (requests of at most 31 days), so a missed morning gets its report and the partial charged and drained totals of the morning are replaced by the complete day. The morning read starts on the day before the check-in day when sleep began after midnight. A failed Body Battery read neither marks the sync partial nor blocks the day: the next refresh tries again, subject to the shared Garmin pause after repeated failures. The one-off wellness history backfill also fills Body Battery reports for past days.
- **Garmin Element Storage**: A Garmin sync stores each element of a collection (a sleep night, a daily summary, a gear item) as its own raw row keyed by the provider's id or calendar day, and writes only the elements that changed; an unchanged element is not rewritten. Activities keep their own rows and tables. The small remainder (fetch times, source freshness, cursors) stays in one small `garmin_state` value. Readers load only the sections and days they need; only the privacy export, which rebuilds `garmin_snapshot.json` from the rows, reads everything. An activity Garmin no longer returns is marked deleted only after an activity read that completed for its whole date range, and only on the range's inner days; a failed, rate-limited or paused read deletes nothing. A full resync merges its state keys, and a payload without a readable fetch time updates the state only. Gear is identified by its `gearUUID`.
- **Garmin Activity Details**: After each successful automatic or manual Garmin sync, the details of up to ten recent Garmin activities from the last 90 days load automatically, newest first and read-only; the backfill pauses after a Garmin rate limit, and manual activities are skipped. It waits only for the activity details part both transports serve; a paused splits, heart-rate zone, power zone, exercise set or FIT part pauses only itself.
- **Garmin Capability Pause**: A Garmin source or detail part pauses for 24 hours after three failures in a row of one capability class: rate limited (HTTP 429), not found (HTTP 404) or unsupported. Network errors, timeouts, server errors (5xx) and rejected logins do not count and leave the count unchanged. The count starts again when a pause expires, and a success clears it. Saving a new Garmin Personal API key or Garmin e-mail address, a stored-login check that succeeds, a new Garmin login and the local data purge clear all pauses. The wellness history backfill pauses under its own `wellness_backfill_` names, so it cannot pause the hourly sync.
- **Open-Meteo Weather**: Forecasts are fetched for the athlete's coordinates and cached for 3 hours. For locations in Germany, the first two days use the DWD ICON-D2 model; other locations and the remaining days up to 14 use ECMWF IFS HRES. Air quality comes from the Open-Meteo Air Quality API; the DWD pollen region is resolved from the coordinates through the DWD GeoServer and its levels are read from the DWD open-data feed. Both sources are optional: a failure is logged and the weather forecast is still cached. Attribution: Open-Meteo.com, Copernicus Atmosphere Monitoring Service, and Deutscher Wetterdienst (CC BY 4.0).
- **iCalendar (ICS) Life Constraints**: The external feed is parsed up to 8 weeks out. Events containing `[NO_TRAINING]`, `[NO_INTENSITY]`, or `[SHORT_ONLY]` in their description are tagged as training constraints.
