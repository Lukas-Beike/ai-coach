# Operations, backups and diagnostics

## SQLCipher Encryption
All persistent application state is stored in `/data/intervals-coach.db` encrypted with AES-256 via SQLCipher. The database key is derived from `APP_PASSWORD`. The application will refuse to start without SQLCipher libraries present.

Each pooled database connection uses a 16 MiB page-cache budget to reduce repeated encrypted reads of large histories. The default pool has four readers and one writer (up to 80 MiB of page caches, allocated as needed).

## Maintenance Mode & Database Restoration
When a database restore is initiated:
1. The uploaded backup is first written in 1 MiB chunks to a new staging file in `/data`, so it is never held in memory as a whole; the size limit is enforced while writing. Staging does not touch the live database, and the staging file is removed when the restore ends. If the process is killed first, leftover staging files, unencrypted privacy-export archives and database-backup snapshots stay in `/data` until the next start removes them before any worker runs.
2. The application enters an exclusive maintenance mode, rejecting new incoming API mutations with an HTTP 503 maintenance notice.
3. Active background sync jobs and Coach turns are allowed to finish gracefully.
4. If an active database exists, a timestamped pre-restore copy is saved beside it in `/data` using the name `intervals-coach.db.pre-restore-<timestamp>-<id>`. The restore is refused with HTTP 507 when `/data` lacks the free space for this copy, and a partial copy is deleted.
5. The replacement database must have the current schema (version 25) or a supported released schema from version 21 onward; a version 21 to 24 backup is upgraded on the staged copy during validation, and older, newer or unknown schemas are rejected unchanged (a backup from before release 1.13.41 is refused with a message naming that release). It must also pass SQLite integrity and foreign-key checks. Restored sessions are cleared before it is installed; failed validation rolls back the staged changes.
6. If valid, the new database is swapped into place and the maintenance gate is lifted; if invalid, the original database is preserved without data loss. A storage failure during the copy or swap returns HTTP 507 (disk full) or 500 instead of a validation error and leaves the original database and its WAL files in place.

## Privacy Export & Data Purge
- **Full Privacy Export**: Download a single comprehensive JSON archive containing all stored profile fields, workouts, check-ins, activity notes, and chat history. Export format version 16 also includes the canonical provider tables (provider records, activity sessions with the survivor each deleted merged session keeps, activity records, observations), the canonical activity detail (detail sets, stream channels as decoded point lists with `null` gaps, laps, zone times, strength sets and session analyses) and the canonical sleep periods, zone configurations with decoded limit lists, provider statuses, gear and gear-to-activity links, retired rows included, as JSON Lines, the owning provider and session of each activity note, when known, and the remote links that map local workouts, planned units and competitions to their provider counterparts (including the provider of each competition sync tombstone). Stored sports are exported in the canonical vocabulary (`sport`, `environment` and a lossless `sport_detail`), and planning records name their start and planned duration `starts_at_local` and `planned_duration_s` (since version 8); version 9 adds the canonical power curve, version 10 the session RPE rating time of each activity note, version 11 the lifecycle (`state`, `owner_record_id`) of each observation, version 12 the executed strength sets with the source of each set list, version 13 the athlete's marking of what a session was, version 14 the stored non-secret provider fields, version 15 the heart-rate and power source and the named sensors of each stream set, and version 16 its stored first threshold estimate; credential-like keys are removed from provider payloads before export, and signed download URLs are replaced with a `[redacted]` marker.
- **GPS tracks**: Position channels (`latitude_deg`, `longitude_deg`) of Garmin and Wahoo FIT files are stored as stream channels in the encrypted database and are part of the backup and the privacy export. They are never merged into read models, so the Coach, the activity detail API, diagnostics and logs never see raw coordinates. The switch "GPS-Spuren speichern" (**Mehr** → privacy section, `GET`/`POST /api/privacy/gps`, default on) stops storing positions of newly fetched files; stored tracks stay until the athlete confirms `GPS-SPUREN LÖSCHEN` (`POST /api/privacy/gps/delete`). Turning the switch on again stores positions only for files fetched from then on. The local data purge deletes them with the stream channels. Repeated routes derived from the tracks (`activity_routes` and `activity_routes_state` in the key/value store, written by the canonical backfill stage `activity_routes`) are deleted in the same request when the stored tracks are deleted, including the athlete's route names, and are not rebuilt without tracks (turning the switch off alone keeps them); the Coach and the activity view get only a route label and visit count.
- **Local Data Purge**: Completely wipes all local athlete records from the database, including canonical provider data, and deletes the recovery copies of the database that restores and the Intervals.icu purge of release 2.0.0 saved beside it, together with the purge marker file. The confirmation dialog lists them (count only) before anything is deleted; a copy that cannot be removed is reported. To prevent accidental loss, the action requires entering the exact confirmation phrase `LOKALE DATEN LÖSCHEN`. External accounts (Intervals.icu, Garmin and Wahoo) remain untouched, except that the app's Wahoo grant is revoked at Wahoo before the tokens are wiped (best effort; a failed revoke is reported in the receipt and the purge completes).

## Operational Logging & Diagnostics
- **Sync Job History and Retry Cadence**: The hourly schedule follows `provider_refresh_history.next_retry_at` (exponential, at most 6 hours, never earlier than a provider-named `Retry-After`); a refresh that failed with `auth_required` is not retried automatically until the athlete acts (manual refresh, restart or changed credentials). `garmin_sdk_required` is final and not retried. While a provider's full resync runs, its queued jobs stay queued (no attempt is consumed) and a rejected operation is recorded as `skipped`, not `error`. Completed `sync_jobs` (with their items) are pruned from the hourly maintenance once they are older than 30 days, always keeping the newest 200 jobs; queued, running, failed and partial jobs are never pruned. A backfill chain (history, wellness, ratings, streams) runs the derived passes (local load, canonical backfill, Wahoo metric export) once when its last batch ends, and a Coach refresh that waited or a full resync requests them when it finishes.
- **Sanitized Logs**: Standard container logs contain only operational timestamps, correlation IDs, status codes, and anonymized error classifications. API tokens, passwords, and athlete metrics are never logged.
- **Always-on Technical Diagnostics**: The application keeps up to 10,000 recent diagnostic entries (16 MiB total, 1 MiB per entry, with truncation marked), including sanitized Coach requests, provider responses, tool activity, and classified provider error details such as status, error code and request ID. Raw OpenAI error text is not stored. Credentials, keys, tokens, and session data are removed before storage.
- **Server Log Management**: In **Betrieb & Diagnose**, authenticated users can download the sanitized current server log and its available rotations as JSON Lines, or delete the log files.
- **Diagnostics Management**: In **Betrieb & Diagnose**, authenticated users can download the sanitized technical diagnostic report as JSON, or clear the stored technical diagnostic entries.
- **Canonical Coverage Summary**: The diagnostic report includes a `canonical_coverage` section with per-provider counts only: activities, observations, issue counts per reason, and whether a sync time is stored. It contains no dates or record content. If the summary cannot be computed, the section reports `unavailable` without details.
- **Canonical Backfill Status**: The diagnostic report includes a `canonical_backfill` section next to `canonical_coverage`. Providers write their canonical rows live; the backfill only re-projects them. Active provider records whose mapper version is behind the current version are re-projected from their stored raw data, in batches. Re-projection never revives a deleted activity, and leaves an activity whose session is deleted untouched. When the new projection no longer emits an activity that an active raw record owns, that activity becomes `invalid` (its session keeps its state) and is counted as `retired`; a later mapper version that emits it again makes it `active` with the same id, counted as `reprojected`. Observations are not retired: an observation that an upgraded mapper no longer emits keeps its old `mapper_version`. While a re-projection is pending, the table reader serves each observation at the newest version stored for it, so nothing disappears; once the backfill completes it serves only observations at the current version. A mapper-version change during a partial re-projection restarts the re-projection scan, including records already passed by the interrupted run. Rows of a provider without a mapper, such as Intervals.icu rows of a database restored from a release before 2.0.0, are left as they are. Temporary writer contention waits and retries the same batch. The section reports `status` (`pending`, `running`, `complete`, or `failed`), the number of `batches`, and per-provider counters: `skipped_invalid`, `duplicates`, `reprojected`, and `retired`. It contains counts only, never activity ids, names, or dates. A `failed` canonical run retries from its saved cursor after a delay; follow-up stages resume on the next pass. If the status cannot be read, the section reports `unavailable`. Activity details are served only from the canonical tables as `activity_detail.v1` for every provider.
- **Canonical Provider Composition**: The diagnostic report includes a `canonical_provider_composition` section (`status` `available`, or `unavailable` without details when a count fails). `sessions.total` counts the surviving canonical sessions and `sessions.by_providers` counts them by the providers of their active records (for example `garmin+intervals`). `sessions.intervals_only` counts the sessions backed only by Intervals.icu records (`total`, `by_year`, `by_source`, `by_year_and_source`); the source is the Intervals.icu `source` value such as `ZWIFT` or `MANUAL`, `unknown` when the raw record has none, and `other` for text outside that enum. `observations.by_kind` counts per metric (and sport) the days with active Intervals.icu observations, the days no other source holds (`intervals_only_days`, also by year) and the days other providers or local values hold (`other_days`); `observations.only_from_intervals` lists the kinds no other source holds at all, and `observations.unrecognized_kinds` only counts stored kinds outside the vocabulary. `domain_rows` counts active sleep period, zone configuration and power curve rows per provider (`local` for rows without one). The section carries counts, years and vocabulary identifiers only, never ids, names, dates or values.
- **Session Focus Backfill**: Once per version the canonical backfill worker runs a last stage that stores the derived session focus (and the strength intensity) on future planned units that lack it, only where the derivation is unambiguous. Past, archived and contested units stay untouched, no exercises are invented, the sync state is kept and no provider is written. The diagnostic report shows `session_focus_backfill` with `status`, `version`, `counts` (`focus`, `intensity`, `undecided`) and `undone`. The changes are recorded in the change history; the authenticated `POST /api/change-history/undo-focus-backfill` restores all of them in one transaction, or none when a unit was edited since.
- **Retired Weekly Plan Removal**: The profile no longer has a weekly plan. A last stage of the canonical backfill worker deletes the old `weekly_plan` key from the stored profile once (state key `profile_weekly_plan_removal_state`); a database restored from an older backup runs it again, and every profile read and save ignores the field meanwhile. The diagnostic report shows `profile_weekly_plan_removal` with `status`, `version` and `removed`.
- **Garmin Snapshot Size**: The diagnostic report includes `database.garmin_snapshot_bytes`, the UTF-8 byte size of the stored `garmin_snapshot` value (`0` when absent). SQL measures this without loading or parsing the payload in Python; the report adds only the byte count. This is a stored-payload measurement, not the process's RAM usage.
- **Runtime Memory Diagnostics**: The diagnostic export adds `runtime.process_memory`: available Linux RSS, peak RSS, locked/anonymous/file memory and virtual bytes, thread count, mapping count and kernel mapping limit. Only numeric counters are exported; process memory, mapping addresses and file paths are never captured. Unavailable OS counters are omitted. Sync start, completion and failure log events include the same counters for before/after comparisons; the snapshot byte count is measured only for the diagnostic report.
- **Stalled Server Stack Dump**: `docker kill -s USR1 pacecraft` writes the stack of every Python thread to the container log (`docker logs`) without stopping the process. The dump contains file names, line numbers and function names only, no variable values. Capture it before restarting a container whose health check times out.
- **Database Memory Budget**: Each pooled SQLCipher connection targets a 16 MiB decrypted-page cache. SQLite's cache target is not a hard process RAM limit: Python objects, query results and other native allocations use additional memory. The database file stays encrypted; `cipher_memory_security` is OFF because locking every SQLCipher allocation in memory fragmented the process into tens of thousands of mappings until allocations failed near the kernel's `vm.max_map_count`. A larger host `vm.max_map_count` can provide temporary mapping headroom but does not correct memory growth.
- **Garmin Metadata Reads**: Automatic sync-window selection, current Morning Body Battery, daily planning and the nutrition day and week energy summaries extract only their required snapshot fields in SQL. Unrelated Garmin collections are not decoded into Python objects for these reads; full sync/merge reads and the stored history remain intact. **Analyse**, `/api/performance` and the Coach performance and recovery sections read Garmin values only from the canonical tables and take only the small stored sync status (freshness, fetch times, read windows) from `garmin_state`.
- **Canonical Read Source**: The diagnostic report includes a `canonical_read` section that names the source serving reads (`tables`, or `pending` while nothing is served yet), the `reason`, and whether the stored check matches the current digest. Reads come from the canonical tables once the backfill has completed at least once; a content-free marker in the backfill state records that, and an existing `complete` state counts as completed. Until then, for example right after an upgrade, reads return no values and **Analyse → Leistung** and the Coach report that data is being prepared instead of partial values. A failed first backfill is reported and retried automatically after a delay from its last committed cursor. After the first completion a mapper-version or time-zone change re-projects the stored records in the background while reads stay on the tables, and a sync inside the running process is written to the tables as it happens. Coverage is served from the summaries persisted at ingest; before the first completion only current summaries are reported. The section reports `serving`, `reason` and `digest_current` (false while a re-projection is pending), and reports `unavailable` if its state cannot be read.
