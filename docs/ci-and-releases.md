# Continuous integration and releases

- **Gitar Reviews**: The installed Gitar GitHub App provides the required `Gitar` check for the current PR head. An isolated ruleset requires this context from `gitar-bot` (integration ID `827041`) on `develop` and `main`; Dependabot and the release app are exempt from that ruleset. Default and Main release protection separately require their CI checks and all review conversations to be resolved, including outdated threads. The release app is not exempt from either of those rulesets. Each ruleset also has an existing user-level pull-request bypass. Fix or reconcile findings before resolving threads. Ordinary PR comments have no resolved state: complete their requested action or record an evidence-based disposition before merging. Hosted automatic review settings are managed in Gitar; disable the former automatic Codex review in [Codex Settings](https://chatgpt.com/codex/settings/code-review) if it is still enabled. Local review remains optional additional evidence.
- **Dependency Updates**: Dependabot updates pip, npm, Docker and GitHub Actions on `develop`, offering a new version only after a 3-day cooldown so a compromised release has time to be pulled. Squash auto-merge is enabled for patch, minor and major updates; protected-branch checks and review-thread resolution still apply. The privileged auto-merge workflow never checks out or executes PR code. Dependabot runs receive no secrets, so after each push to `develop` and hourly the auto-rebase workflow uses the trusted `develop` copy of `tools/quality_baseline.py --align-versions` to read open Dependabot PR files as data and commits only the aligned tool-version record through the GitHub App, rejecting the commit if the PR head moved after the reads.
- **Automated Daily Releases**: At 03:00 UTC, an automated workflow inspects `develop`. If new commits exist and no open issue or PR carries the `release-blocker` label, it creates a version-bump PR and a promotion PR to protected `main`. Both branches require their configured test, quality and browser checks; the release app cannot bypass those requirements. After successful main tests, the workflow creates an immutable GitHub release and publishes the container: the release run pushes the exact `pacecraft:ci` image its test, browser and SBOM jobs used (no rebuild) and attaches that SBOM as a signed attestation. The container digest is signed and verified before promoting `latest`; the version tag and `latest` must resolve to that same digest. While any `release-blocker` item is open, the scheduled run skips the bump and promotion and names the blockers in its job summary; if that label query fails, the run fails without releasing. Add the label to the blocking fix's issue or PR and remove it (or close the item) to resume. Manual dispatch is not gated. A read-only release preflight also verifies `APP_VERSION` before its tag exists. Actions use read-only default permissions, with explicit job-level write permissions where needed.
- **GitHub Pages**: The project site in `site/` deploys only from `main` (or a manual dispatch), so unreleased site changes on `develop` stay private until the release; the `github-pages` environment allows only `main`.
- **Run cancellation**: A newer push to the same PR cancels that PR's older test-and-publish run; push, release and dispatch runs always finish.
