# Provider endpoints

The normative table of every outbound provider call. A change that adds, removes or alters a call updates this file in the same pull request. Callers are `file:symbol` paths relative to `backend/`; a use case is named where the client method is shared. Provider behaviour beyond the transport (authorization, status cards, what is stored) is in the specs under `openspec/specs/provider-connections/`.

## Common transport

- **Shared JSON client** (`providers/http.py:JsonHttpClient.request`): Intervals.icu, Wahoo (API and OAuth), Open-Meteo, DWD, OpenAI (JSON and audio) and the connection-check probes. Default timeout 45 s, overridden per call (shown per row). Response body cap 10,000,000 bytes (`MAX_EXTERNAL_RESPONSE_BYTES`). Redirects are refused (`urlopen` with `_RejectProviderRedirects`), so credentials never follow a redirect. The transport never retries.
- **Own transports** with the same redirect refusal: Garmin Personal API (`providers/garmin_personal.py:GarminPersonalClient._open`), Yazio and Open Food Facts (`request_json`, observed through `providers/observed_opener.py`), the Wahoo FIT download, the OpenAI and Claude streams, the Claude model listing. The calendar feed uses a raw TLS socket with its own limits. The Garmin SDK (`garminconnect`) does its own HTTP; the app sets no timeout on it.
- **Error mapping of the shared client** ("shared" in the tables). `{label}` is `Garmin` or `Intervals.icu`, `Der externe Kalender` for the calendar and `Der externe Dienst` for every other service.

| Failure | Public status, reason | Message |
| --- | --- | --- |
| HTTP error from the provider | 401/403 502 `upstream_auth`; 404 502 `upstream_not_found`; 429 429 `upstream_rate_limited`; 408 and 5xx 503 `upstream_unavailable`; other 502 `upstream_rejected` (`errors.py:upstream_public_status`); internal reason `provider_http_error` | `Anfrage an externen Dienst fehlgeschlagen ({code}).`; Intervals.icu with a readable error body: `Intervals.icu weist die Anfrage zurück ({code}): {detail}` |
| Network error or timeout | 502 `provider_network_error` | `{label} ist nicht erreichbar.` |
| Unreadable answer or other exception | 502 `provider_client_error` | `Die Antwort von {label} konnte nicht verarbeitet werden.` |
| Answer over the body cap | 502 | `Die Antwort des externen Dienstes ist zu groß.` |
| Cancelled by the caller | 499 `chat_cancelled` | `Die Coach-Anfrage wurde abgebrochen.` |

- **SDK and Personal API calls** run inside `providers/http.py:external_call`: any non-`AppError` becomes 502 `provider_client_error` with the original as cause. Three failures in a row of one capability class (429, 404, unsupported) pause that Garmin source for 24 hours (`sync/garmin.py:GARMIN_CAPABILITY_FAILURE_LIMIT`); other failures never count.
- **Job-level retry** is the only backoff (`sync/jobs.py`, `sync/job_outcomes.py:record_failure`, constants in `server.py`): at most 3 attempts (`SYNC_JOB_MAX_ATTEMPTS`), delay 900 s x 2^(attempt-1) capped at 21,600 s, raised to a provider-named `Retry-After` (also capped). Only the classes `network_error`, `database_busy`, `timeout`, `provider_unavailable`, `rate_limited`, `temporary_error` and `process_interrupted` are retried; `auth_required` and `invalid_configuration` never are (`sync/refresh.py:ProviderRefreshTracker.error_code`). Scheduled refresh history backs off the same way (`sync/refresh.py:retry_at`, exponent capped at 2^5). A call outside a job (an HTTP request, a connection check, a login) is not retried.
- **Cancel**: a `cancel_event` passed to the shared client aborts the request and reads with 499; SDK and Personal calls check it between calls only.

## Intervals.icu

Intervals.icu is an output target only. The app never reads activities or wellness history from it. Its only reads are:

- read-backs of explicit exports: the library list and folders of a library push (rows I1, I2), a calendar event by id (row I11);
- the calendar events inside an explicit push: the competition window and the repair window (rows I9, I10);
- the one-day metric-export reads: the wellness record of one day and the sport settings of Ride or Run, only for values offered for export (rows I14, I15);
- the explicit connection check (row I19).

Base `https://intervals.icu/api/v1`, Basic auth user `API_KEY`, paths with `{id}` = `INTERVALS_ATHLETE_ID`, `<sport>` = `Ride` or `Run`. Methods are on `providers/intervals_client.py:IntervalsClient` unless named. All rows: timeout 45 s, no retry. Paged reads (`providers/intervals.py:fetch_paged_collection`) ask 500 rows per page with `limit` and `offset`, stop after 100 pages and fail with the English messages `Invalid {collection} page`, `Invalid {collection} records`, `Repeated {collection} page` and `Page limit exceeded for {collection}.` (502).

## Garmin Personal API

Official read-only API, base `https://personal.connectapi.garmin.com`. Used whenever a Personal API key is configured, for the methods in `providers/garmin_personal.py:PERSONAL_METHODS`; without a key the same method names go to the SDK (see the SDK section). All rows: timeout 45 s, body cap 10,000,000 bytes (FIT archive 50,000,000), `Authorization: Bearer <token>`. Retry: one fresh token exchange after a 401, nothing else. HTTP errors become `ProviderHTTPError` with category `rate_limited` (429, carries `Retry-After`), `authentication` (401, 403) or `http`; the body is never read. Through `external_call` they reach the caller as the 502 `provider_client_error` of the common table (`Die Antwort von Garmin konnte nicht verarbeitet werden.`). Windowed reads split into inclusive windows of 31 days.

## Weather: Open-Meteo and DWD

Shared JSON client, timeout 10 s, no retry inside the call. The forecast cache is fresh for 10,800 s; after a failure the next refresh waits 900 s x 2^(failures-1), capped at 21,600 s (`weather/service.py:WeatherRetryPolicy`).
